## <font color="#87CEEB">0. Introducción — La otra cara de la seguridad: el endpoint</font>

<hr style="border: none; height: 10px; background-color: #003b00;" />

En tema03 se explotaron servicios vulnerables. En tema04 se emuló un adversario real (OilRig).
En tema05 se aprendió a **investigar** amenazas con un TIM. En este tema se da un paso que
hasta ahora no se había dado: se mira hacia **adentro**, al endpoint mismo — el lugar donde
todo ataque finalmente aterriza (una laptop, un servidor, un computador personal).

Un endpoint Windows no es una caja negra indefensa. Trae **capas de seguridad nativas**
apiladas: identidad y control de acceso, control de privilegios, antimalware, firewall,
logging. Un analista defensivo (blue team) no necesita instalar nada exótico para empezar:
necesita saber **dónde mirar** y **qué pregunta hacerle a cada capa**.

En esta clase se audita la postura de seguridad de **un host Windows real propio**,
usando una cuenta **estándar** (no administrador) — exactamente el privilegio con el que
trabaja la mayoría de usuarios en una organización, y el mismo con el que opera un atacante
justo después de comprometer una cuenta de empleado.

> **Idea clave:** no se ataca nada. Se sigue, paso a paso, la ruta que **tomaría** un
> atacante después de obtener acceso a este endpoint — y en cada paso el análisis se detiene a
> observar qué capa de Windows lo **frena**, lo **detecta** o lo **registra**. Cero
> ofensiva, máximo aprendizaje de ATT&CK desde el lado de la defensa.

Esta clase conecta directo con tema05: allí se cargaron técnicas MITRE ATT&CK en el TIM
(OpenCTI). Aquí cada mecanismo de defensa que se encuentre se mapea a la técnica ATT&CK que
detecta o mitiga — y al final se podrán cruzar esas técnicas en el TIM propio para
ver qué actores y malware reales las usan.

> **Valor de la sesión:** al terminar, cada alumno entrega un **informe de postura de
> seguridad** de su propio host, con cada hallazgo de defensa mapeado a la técnica ATT&CK
> correspondiente.

**Ruta de la clase (3 horas):**

| Bloque | Tiempo | Qué se hace |
| ------ | ------ | --------- |
| Bloque 1 — Identidad y privilegios | 60 min | Se audita la identidad Windows: SID, grupos, privilegios, integrity levels, UAC y ACLs NTFS. |
| Bloque 2 — Superficie y defensa activa | 75 min | Se inspeccionan autoarranques, servicios, Windows Defender y Firewall: qué detendría o registraría un ataque. |
| Bloque 3 — Telemetría y auditoría | 45 min | Se revisan Event Viewer, Process Explorer y TCPView, y se consolida el informe de postura. |

## <font color="#87CEEB">1. Requisitos y preparación</font>

<hr style="border: none; height: 10px; background-color: #003b00;" />

- **Host:** un Windows 10 u 11 real (laptop personal, VM personal, o el equipo de uso
  diario). No es un laboratorio con OVA — es **un endpoint propio**.
- **Cuenta:** una cuenta **estándar** (no administrador) es suficiente para completar el
  **flujo principal** de los 3 bloques. Tener admin es opcional; si se cuenta con él, los
  bloques desglosables (colapsables) dan la vista completa de privilegios elevados.
- **Sysinternals portables (offline):** se descarga **SysinternalsSuite.zip** desde
  `https://learn.microsoft.com/sysinternals/downloads/sysinternals-suite` **una sola vez**
  con internet, se copia a un USB, se descomprime y se ejecutan los `.exe` directamente — no
  requieren instalación. Las herramientas empleadas son: **Autoruns**, **Process Explorer**,
  **TCPView** y **AccessChk**.

> ⚠️ **Algunas vistas completas requieren "Ejecutar como administrador".** Cada ejercicio
> marca explícitamente esos comandos dentro de un bloque desglosable (colapsable). Fuera de
> eso, el laboratorio **no necesita internet** una vez que Sysinternals está en el USB.

> **Nota de seguridad y ética:** todo lo que se haga hoy es sobre **el host propio** y es
> puramente de **inspección/lectura**. Los pocos cambios de configuración que se activan
> (logging del firewall) están marcados como reversibles y **se revierten al final** en
> la Sección 6. Nunca se debe ejecutar nada de esta clase contra un equipo que no sea el propio.

## <font color="#87CEEB">2. Identidad y privilegios (60 min)</font>

<hr style="border: none; height: 10px; background-color: #003b00;" />

### 2.1 Concepto — SID, grupos, privilegios, integrity levels y UAC

Windows controla el acceso con cinco piezas que trabajan juntas:

| Pieza | Qué es |
| ----- | ------ |
| **SID** (Security Identifier) | Identificador único e irrepetible de la cuenta o grupo del usuario — la ACL nunca guarda el nombre, guarda el SID. |
| **Grupos** | Conjuntos de cuentas (Users, Administrators, Remote Desktop Users…) que heredan permisos colectivos. |
| **Privilegios** | Derechos individuales sobre el sistema (ej. `SeDebugPrivilege`, `SeBackupPrivilege`) — distintos de los permisos sobre un objeto. |
| **Integrity Level (Mandatory Integrity Control)** | Etiqueta de confianza del proceso: `Low < Medium < High < System`. Un proceso Medium (la cuenta estándar del usuario) no puede escribir sobre un objeto marcado High sin pasar por UAC. |
| **UAC** (User Account Control) | El "portero" que exige consentimiento explícito para que un proceso salte de Medium a High. |

Un atacante que compromete la cuenta de un usuario hereda exactamente el SID, los grupos, los
privilegios y el integrity level de esa cuenta — nada más. Esa es la razón por la que "cuenta
estándar por defecto" es una de las mitigaciones más baratas y efectivas que existen.

Conviene observar tres cosas: el **SID** (`S-1-5-21-...-1001`), la lista de **grupos**, y la

> **Hallazgo real de este host — el "token dividido" de UAC:** se observan dos líneas clave:
> `NT AUTHORITY\Local account and member of Administrators group` y `BUILTIN\Administrators`,
> **ambas marcadas `Group used for deny only`**. Esta cuenta (`jarod`) *sí* es administrador,
> pero Windows le entregó un **token filtrado** (integridad Media) donde el grupo
> `Administrators` está presente pero **deshabilitado para negar**. Esto es **UAC Admin
> Approval Mode**: incluso un admin navega el día a día en Media, y solo obtiene el token
> completo (integridad Alta) tras aprobar un prompt de UAC ("Ejecutar como administrador").
> Una cuenta estándar *pura* ni siquiera tendría el grupo `Administrators`. En **ambos casos**
> el proceso corre en integridad Media — que es justo el nivel que hereda un atacante que
> compromete la sesión. Por eso "trabajar en Media por defecto" es la mitigación barata.

### 2.3 ACLs NTFS — qué se puede escribir y qué no

```powershell
icacls C:\Users\%USERNAME%\Documents
```

```text
.\Documents\ NT AUTHORITY\SYSTEM:(I)(OI)(CI)(F)
             BUILTIN\Administrators:(I)(OI)(CI)(F)
             DESKTOP-6FC3LBH\jarod:(I)(OI)(CI)(F)
```

Las siglas se descifran así: `(F)` = Full control, `(OI)` = Object Inherit, `(CI)` = Container
Inherit, `(I)` = permiso **heredado** de la carpeta padre. La carpeta `Documents` otorga
control total (`jarod:(F)`) — un atacante con esa cuenta puede escribir aquí libremente.

```powershell
icacls C:\Windows\System32
```

```text
C:\Windows\System32 NT SERVICE\TrustedInstaller:(F)
                    NT AUTHORITY\SYSTEM:(M)
                    BUILTIN\Administrators:(M)
                    BUILTIN\Users:(RX)
                    CREATOR OWNER:(OI)(CI)(IO)(F)
                    APPLICATION PACKAGE AUTHORITY\ALL APPLICATION PACKAGES:(RX)
```

**Este es el contraste clave.** Sobre `Documents` la cuenta del usuario tenía `(F)` (control
total); sobre `C:\Windows\System32`:
- **`TrustedInstaller:(F)`** — solo el servicio *Windows Modules Installer* tiene control total.
  Ni siquiera `Administrators` puede modificar `System32` sin antes apropiarse de la ruta.
- **`SYSTEM` y `Administrators:(M)`** — Modify, pero no Full (no pueden cambiar el dueño).
- **`BUILTIN\Users:(RX)`** — la cuenta estándar: solo **leer y ejecutar**, **nada de escritura**.

Esa fila `Users:(RX)` es la barrera NTFS en acción: un atacante con esa cuenta puede *ejecutar*
lo que hay en `System32`, pero **no puede plantar** un binario malicioso ahí — necesita primero
escalar privilegios. Al contrastarlo con `Documents` (`jarod:(F)`), queda claro que ahí sí se
puede escribir libremente.

> **Nota:** en la corrida anterior se usó `icacls C:` (raíz del disco), donde `jarod` aparecía
> con `(F)` — atípico y anotable, pero es la raíz, no una ruta de sistema protegida. `System32`
> muestra el modelo correcto: `TrustedInstaller` manda, `Users` solo lee/ejecuta.

### 2.4 AccessChk (Sysinternals) — permisos efectivos

```cmd
accesschk.exe -accepteula -w C:\Users\%USERNAME%\Documents
```

> **Nota de laboratorio — cómo invocarlo:** los binarios de Sysinternals son portables (no se
> instalan). Se hace `cd` a la carpeta donde se descomprimieron y se los invoca con `.\` por
> delante — PowerShell, a diferencia de CMD, **no** busca ejecutables en el directorio actual
> por defecto (medida contra secuestro de binarios). Si se omite el `.\` aparece
> `The term 'accesschk.exe' is not recognized`.

```powershell
cd C:\SysinternalsSuite
.\accesschk.exe -accepteula -w C:\Users\$env:USERNAME\Documents\
```

```text
Accesschk v6.15 - Reports effective permissions for securable objects

C:\Users\jarod\Documents\elastic-agent-9.3.3+build...-windows-x86_64
  RW NT AUTHORITY\SYSTEM
  RW BUILTIN\Administrators
  RW DESKTOP-6FC3LBH\jarod
C:\Users\jarod\Documents\ollerenacastro.github.io
  RW NT AUTHORITY\SYSTEM
  RW BUILTIN\Administrators
  RW DESKTOP-6FC3LBH\jarod
...
```

El flag `-w` lista solo lo **escribible** (`RW`). Cada carpeta bajo `Documents` es escribible
por `jarod` — confirma lo que se vio con `icacls`: el perfil del usuario es su zona de
escritura, y también la de un atacante con esa cuenta.

> **Hallazgo curioso:** entre las carpetas escribibles aparecen `elastic-agent-9.3.3...` (el
> instalador del EDR que se vio corriendo en `Get-Service`) y `ollerenacastro.github.io` (¡el
> propio repositorio de este curso!) — ambos en `Documents`. Recordatorio de que las
> herramientas de seguridad y los proyectos suelen vivir en rutas de usuario escribibles: un
> atacante que quiera sabotear el EDR o inyectar en un binario del proyecto no necesita más
> privilegio que el de esa cuenta. Conviene mantener `Documents` limpio de binarios sensibles.

`accesschk` resuelve permisos efectivos (herencia + grupos incluidos) mejor que `icacls` a
simple vista — útil para confirmar rápido qué rutas del sistema son realmente escribibles
por la cuenta del usuario.

```text
SeCreateGlobalPrivilege                   Create global objects                        Enabled
...  (24 en total)
```

> **Este es el corazón de UAC, visto en vivo.** El **mismo usuario**, el **mismo comando** —
> dos tokens distintos. En Media: 5 privilegios inofensivos. En Alta, tras aprobar el prompt de
> UAC, aparecen los que un atacante codicia:
> - **`SeDebugPrivilege: Enabled`** — adjuntarse a **cualquier** proceso, incluso de SYSTEM
>   (así funciona el volcado de credenciales de LSASS — T1003).
> - **`SeImpersonatePrivilege: Enabled`** — suplantar tokens; la base de familias de exploits
>   "Potato" para escalar a SYSTEM (T1134).
> - **`SeBackupPrivilege` / `SeRestorePrivilege` / `SeTakeOwnershipPrivilege`** — leer o
>   apropiarse de cualquier archivo ignorando las ACLs.
>
> Que el token **filtrado** (el del día a día) **no** exponga estos privilegios es exactamente
> la barrera de UAC. Un bypass de UAC no "crea" estos poderes: solo salta el prompt que
> separa un token del otro. Por eso el consentimiento de elevación es una frontera de seguridad,
> no un simple diálogo molesto.

```cmd
net user Administrator
```

```text
User name                    Administrator
Comment                      Built-in account for administering the computer/domain
Account active               No
Account expires              Never
Password last set            7/26/2026 8:02:09 AM

```

> **Buena postura:** la cuenta integrada `Administrator` está **`Account active: No`** — Windows
> la deshabilita por defecto, y así debe quedar. Es un objetivo clásico de fuerza bruta (SID
> conocido, termina en `-500`); mantenerla desactivada elimina ese vector. Con admin también se
> pueden listar los perfiles de otros usuarios (`C:\Users\<otro>`) — como estándar, `icacls`
> devuelve acceso denegado sobre la mayoría de esas carpetas.

### 2.6 Qué frena / qué registra

- **UAC + Integrity Levels** impiden que un proceso Medium modifique un objeto marcado High
  sin consentimiento explícito del usuario — incluso si el atacante logró ejecutar código
  con la cuenta del usuario, sigue atrapado en Medium hasta que alguien apruebe la elevación.
- **ACLs NTFS** niegan escritura sobre rutas del sistema (`System32`, `Program Files`)
  aunque el atacante tenga ejecución de código arbitrario, mientras su proceso siga en el
  integrity level de una cuenta estándar.

### 2.7 Mapeo ATT&CK

| Técnica ATT&CK | Nombre | Por qué aplica aquí |
| -------------- | ------ | -------------------- |
| **T1078** | Valid Accounts | El atacante opera con credenciales legítimas robadas — la identidad del usuario, sus permisos. |
| **T1134** | Access Token Manipulation | Manipular tokens/privilegios para operar como otro usuario o proceso. |
| **T1548** | Abuse Elevation Control Mechanism (UAC bypass) | El prompt de UAC es exactamente lo que un atacante intenta evadir para pasar de Medium a High. |

> **Entregable parcial 1:** el mapa de identidad (usuario, SID, grupos, integrity level) más
> la tabla comparativa de permisos NTFS sobre `Documents` vs. `System32`.

## <font color="#87CEEB">3. Superficie y defensa activa (75 min)</font>

<hr style="border: none; height: 10px; background-color: #003b00;" />

### 3.1 Concepto — persistencia, ejecución y las capas que las vigilan

Si un atacante ya ejecutó código en el endpoint, su siguiente objetivo suele ser
**persistir** (sobrevivir a un reinicio) y evitar ser **detenido**. Windows expone tres
capas para observar exactamente eso: **autoarranques** (dónde algo puede persistir),
**Windows Defender** (qué bloquea/detecta) y **Windows Firewall** (qué conexión entrante
filtra). Las tres son consultables como usuario estándar.

### 3.2 Autoruns — dónde persiste el software al arrancar

Se ejecuta `Autoruns64.exe` desde el USB (sin instalar). Como usuario estándar se muestran las
entradas del perfil propio (`HKCU`) y buena parte de las globales (`HKLM`) en solo
lectura. Se activan **Options → Verify Code Signatures** y **Options → Hide Microsoft Entries**
para reducir el ruido y enfocarse en lo firmado vs. no firmado.

![Autoruns mostrando entradas de arranque filtradas por firma](/assets/images/tema06/autoruns01.png)

> **¿Qué es la pestaña "Logon"?** Autoruns agrupa los autoarranques en pestañas. La pestaña
> **Logon** lista lo que se ejecuta **cada vez que se inicia sesión**: las claves de registro
> `Run` / `RunOnce` (de `HKCU` para el usuario y `HKLM` para todo el equipo) y la carpeta
> *Startup* del menú Inicio. Es la ubicación de persistencia #1 que buscan tanto el software
> legítimo (el antivirus, OneDrive, drivers) como el malware. Con **Verify Code Signatures**
> activado, cada fila muestra el firmante; **`(Not verified)`** en rojo = binario sin firma
> válida → sospechoso.
>
> **Tarea de informe:** se anota cuántas entradas aparecen en la pestaña *Logon* y si alguna
> sale como `(Not verified)`. Se compara con la captura de arriba.

Los atacantes prefieren las claves `Run`/`RunOnce` del registro, servicios y tareas
programadas precisamente porque sobreviven a un reinicio sin intervención humana.

### 3.3 Servicios — firmados vs. no firmados

```powershell
Get-Service | Where-Object {$_.Status -eq 'Running'}
```

La lista completa supera los 250 servicios. Extracto de los relevantes para seguridad que
están **`Running`** en el host de prueba:

```text
Running  WinDefend          Microsoft Defender Antivirus Service
Running  WdNisSvc           Microsoft Defender Antivirus Network Inspection Service
```

> **Hallazgo real — este host ya tiene un stack de detección montado:** dos servicios saltan
> a la vista:
> - **`Sysmon64`** — System Monitor (Sysinternals). Registra creación de procesos, conexiones
>   de red, cambios en registro… la telemetría de endpoint que se emplea en el **Bloque 3**.
> - **`Elastic Agent`** — un agente EDR/SIEM que envía esa telemetría a un servidor central.
>
> Que ambos estén `Running` significa que este endpoint ya está **instrumentado**: cada acción
> del atacante dejaría rastro. Al compararlo con `mpssvc` (firewall) + `WinDefend` (antivirus) +
> `BFE` (motor de filtrado) también activos, se ve: identidad → defensa → **telemetría**, las
> tres capas encendidas. Destacan además `postgresql-x64-16` y `VBoxService` (delata que es una
> VM): servicios de terceros que amplían la superficie y merecen figurar en el inventario.

También se puede explorar visualmente con `services.msc`. Un servicio ejecutando un binario
**no firmado** (verificable con Autoruns o `Get-AuthenticodeSignature`) es una señal de
alerta: los servicios legítimos de Windows y de fabricantes reconocidos casi siempre están
firmados digitalmente.

> **Lectura de postura (esto está bien):** `RealTimeProtectionEnabled: True` (escaneo en vivo),

> todo esto pero no cambiarlo: perfecto para auditar sin riesgo.

```text
ExclusionProcess               : {N/A: Must be an administrator to view exclusions}
ExclusionExtension             : {N/A: Must be an administrator to view exclusions}
HideExclusionsFromLocalUsers   : True
EnableControlledFolderAccess   : 0
EnableNetworkProtection        : 0
PUAProtection                  : 0
```

> **Hallazgo real — el punto ciego que ama el atacante (T1562):** las tres líneas de exclusión
> devuelven **`{N/A: Must be an administrator to view exclusions}`**. Y `HideExclusionsFromLocalUsers:
> True` confirma que la política **oculta deliberadamente** las exclusiones a los usuarios no
> administradores. Esto corta en ambos sentidos:
> - **Defensivamente**, es buena higiene: un atacante con una cuenta estándar tampoco puede
>   enumerar las exclusiones para esconderse en ellas.
> - **Como auditor**, es una limitación real: para *verificar* que no hay exclusiones maliciosas
>   se necesita una consola elevada (ver desglosable). Una exclusión de ruta/proceso es
>   literalmente decirle al antivirus "no mires aquí" — el escondite favorito del malware.
>
> A vigilar además: `EnableControlledFolderAccess: 0` (protección anti-ransomware **apagada**),
> `EnableNetworkProtection: 0` y `PUAProtection: 0` (bloqueo de apps potencialmente no deseadas
> **apagado**). Tres endurecimientos gratuitos que este host no tiene activados.

<details markdown="1">
<summary>🔐 <strong>Requiere admin</strong> — ver las exclusiones reales de Defender</summary>

Desde una consola elevada, las mismas propiedades muestran los valores reales en vez de
`{N/A: Must be an administrator...}`:

```powershell
Get-MpPreference | Select-Object ExclusionPath,ExclusionProcess,ExclusionExtension
```

Se revisa cada entrada: ¿se reconoce esa ruta/proceso? Una exclusión de `C:\Users\Public\` o de
un `.exe` que no fue instalado por el usuario es una bandera roja de compromiso.

</details>

### 3.6 Windows Firewall — perfiles y reglas (lectura estándar)

```powershell
Get-NetFirewallProfile | Select-Object Name,Enabled,DefaultInboundAction
```

```text
Name    Enabled DefaultInboundAction
----    ------- --------------------
Domain     True        NotConfigured
Private    True        NotConfigured
Public     True        NotConfigured
```

Los tres perfiles están **`Enabled: True`** — el firewall está activo sin importar a qué red
te conectes. `DefaultInboundAction: NotConfigured` significa que se usa el comportamiento por
defecto de Windows: **bloquear** el tráfico entrante que no coincida con una regla explícita
("deny by default", la postura correcta).

```powershell
Get-NetFirewallRule -Direction Inbound -Enabled True | Select-Object -First 20 DisplayName,Action
```

```text
DisplayName                                                   Action
-----------                                                   ------
WFD Driver-only (TCP-In)                                       Allow
Delivery Optimization (TCP-In)                                 Allow
Delivery Optimization (UDP-In)                                 Allow
Connected Devices Platform (UDP-In)                            Allow
Core Networking - Destination Unreachable (ICMPv6-In)          Allow
Core Networking - Neighbor Discovery Solicitation (ICMPv6-In)  Allow
Core Networking - Router Advertisement (ICMPv6-In)             Allow
...
```

Las primeras 20 reglas de entrada son todas de componentes **legítimos de Windows** (Core
Networking, Delivery Optimization, Connected Devices). Como auditor se busca lo que **no**
encaja: una regla `Allow` entrante hacia un puerto alto o un `.exe` desconocido en `AppData`
sería la bandera roja — es una técnica de persistencia (abrir un puerto para el C2).

Windows distingue tres perfiles según qué tan confiable es la red conectada: **Domain**
(equipo unido a un dominio corporativo), **Private** (red doméstica confiable) y **Public**
(red abierta, ej. un café) — cada uno con su propio set de reglas de entrada.

### 3.7 Habilitar logging del firewall (reversible)

<details markdown="1">
<summary>🔐 <strong>Requiere admin</strong> — habilitar logging temporal del firewall</summary>

Antes de cambiar nada, **se anota el valor actual** con
`Get-NetFirewallProfile | Select-Object Name,LogAllowed,LogBlocked` — es necesario para
revertir exactamente al final (Sección 6).

```powershell
Set-NetFirewallProfile -LogAllowed True -LogBlocked True -LogFileName "%systemroot%\system32\LogFiles\Firewall\pfirewall.log"
```

El comando no imprime salida si tiene éxito (vuelve al prompt). Se verifica que el cambio se
aplicó con `Get-NetFirewallProfile | Select-Object Name,LogAllowed,LogBlocked` — ahora debería
mostrar `True`. El log se escribe en `%systemroot%\system32\LogFiles\Firewall\pfirewall.log`.

> ⚠️ **Este cambio es temporal y debe revertirse.** Se anotan los valores originales
> obtenidos arriba — serán necesarios en la Sección 6 (Cierre) para dejar el equipo
> exactamente como estaba. Este es un paso opcional para hacer **en clase** con la consola
> elevada; si se trabaja solo con cuenta estándar, se puede omitir.

</details>

### 3.8 Qué frena / qué registra

- **Windows Defender** bloquea o aísla ejecución maliciosa detectada por firma o
  heurística — salvo que exista una exclusión que la esté ignorando.
- **Windows Firewall** filtra conexiones **entrantes** según el perfil de red activo,
  reduciendo la superficie expuesta a movimiento lateral.
- **Autoruns** revela mecanismos de persistencia que sobrevivirían a un reinicio.

### 3.9 Mapeo ATT&CK

| Técnica ATT&CK | Nombre | Por qué aplica aquí |
| -------------- | ------ | -------------------- |
| **T1547** | Boot or Logon Autostart Execution | Claves `Run`, tareas programadas y entradas de arranque visibles en Autoruns. |
| **T1543** | Create or Modify System Process | Servicios usados para persistir y ejecutar con privilegios de sistema. |
| **T1562** | Impair Defenses | Exclusiones de Defender o deshabilitar protección en tiempo real. |
| **T1021** | Remote Services | El Firewall gobierna qué servicios remotos (RDP, SMB) quedan expuestos para movimiento lateral. |

> **Entregable parcial 2:** el inventario de autoarranques (firmados vs. no) más el estado
> de Defender y Firewall (protección activa, exclusiones, perfiles y reglas de entrada).

## <font color="#87CEEB">4. Telemetría y auditoría (45 min)</font>

<hr style="border: none; height: 10px; background-color: #003b00;" />

### 4.1 Concepto — la última capa: qué queda registrado

Si un atacante logró ejecutar y persistir sin ser bloqueado, la última línea de defensa es
la **telemetría**: los rastros que su actividad deja en logs de eventos, en la lista de
procesos y en las conexiones de red activas. Esta capa no previene — **detecta y permite
reconstruir** lo que pasó.

### 4.2 Event Viewer — eventos de logon (4624 / 4625)

El **Visor de eventos** (`eventvwr.msc`), log **Seguridad**, registra cada intento de
inicio de sesión: el evento **4624** marca un logon **exitoso**, el **4625** un logon
**fallido**. Un patrón de múltiples 4625 seguido de un 4624 sobre la misma cuenta es la
huella clásica de un ataque de fuerza bruta o password spraying que finalmente tuvo éxito.

![Visor de eventos mostrando el log de Seguridad con eventos de logon](/assets/images/tema06/eventviewer01.png)

> **Hallazgo real de este host:** en la ventana consultada **no hay eventos 4625** (ningún
> logon fallido) — solo 4624 (éxitos). Y todos los 4624 recientes son **Logon Type 5**
> (inicio de un **servicio**), de la cuenta `SYSTEM` vía `services.exe`. Es exactamente lo que
> esperas de un equipo que acaba de arrancar sus servicios: ruido de fondo legítimo, cero
> intentos fallidos. La ausencia de 4625 es en sí un dato — si de pronto aparecen decenas de
> 4625 sobre una cuenta, esa es la firma de un ataque de fuerza bruta en curso.

### 4.3 Consultar el log de Seguridad y la política de auditoría

<details markdown="1">
<summary>🔐 <strong>Requiere admin</strong> — consultar el log de Seguridad vía PowerShell</summary>

Leer el log **Seguridad** por línea de comandos normalmente exige una consola elevada
(por ACL del propio log, reservado a `Administrators`/`Event Log Readers`/`SYSTEM`).

```powershell
Get-WinEvent -LogName Security -MaxEvents 20 | Where-Object {$_.Id -in 4624,4625} | Select-Object TimeCreated,Id,Message
```

```text
TimeCreated            Id  Message
-----------            --  -------
7/26/2026 8:36:43 AM  4624 An account was successfully logged on.
                            New Logon:   Account Name: SYSTEM  (NT AUTHORITY)
                            Logon Type:  5   (Service)
                            Elevated Token: Yes
                            Process:     C:\Windows\System32\services.exe
7/26/2026 8:36:32 AM  4624 An account was successfully logged on.  (Type 5, SYSTEM)
7/26/2026 8:36:05 AM  4624 An account was successfully logged on.  (Type 5, SYSTEM)
7/26/2026 8:25:32 AM  4624 An account was successfully logged on.  (Type 5, SYSTEM)
```

Cada evento 4624 trae el campo clave **Logon Type**. Conviene memorizar los importantes:

| Logon Type | Significado | Relevancia forense |
| ---------- | ----------- | ------------------ |
| **2** | Interactivo (teclado local) | El usuario se sentó frente al equipo |
| **3** | Red (SMB, recurso compartido) | Acceso remoto a archivos/impresoras |
| **5** | Servicio | Arranque de un servicio (lo que ves aquí) |
| **7** | Desbloqueo de pantalla | Volver de la sesión bloqueada |
| **10** | RemoteInteractive (RDP) | **Escritorio remoto — requiere vigilancia cercana** |

Los eventos de este host son todos **Type 5 / SYSTEM** — ruido de arranque normal. Un
**Type 10** que no se reconozca, o una ráfaga de **Type 3** de madrugada, serían señales para
investigar movimiento lateral.

La **política de auditoría** define qué categorías de eventos se registran (logon,
gestión de cuentas, acceso a objetos, etc.):

```cmd
auditpol /get /category:*
```

> **Ojo con la sintaxis:** son **dos** barras — `auditpol /get /category:*`. Si se omite el `/`
> antes de `category`, devuelve `Error 0x00000057: The parameter is incorrect`.

Extracto de las subcategorías clave del host de prueba:

```text
Logon/Logoff
  Logon                          Success and Failure
  Logoff                         Success
  Special Logon                  Success
Account Management
  Security Group Management      Success
  User Account Management        Success
Detailed Tracking
  Process Creation               No Auditing
  Process Termination            No Auditing
Object Access
  File System                    No Auditing
  Registry                       No Auditing
  SAM                            No Auditing
Privilege Use
  Sensitive Privilege Use        No Auditing
```

> **Lectura de postura — dónde ves y dónde estás ciego:**
> - **`Logon: Success and Failure` ✅** — por esto se registraron los eventos 4624/4625. Si estuviera en
>   `No Auditing`, un ataque de fuerza bruta no dejaría rastro. Está bien configurado.
> - **`User Account Management: Success` ✅** — si un atacante crea una cuenta para persistir
>   (T1136), queda registrado (evento 4720). Bien.
> - **`Process Creation: No Auditing` ⚠️** — Windows **no** está registrando el evento nativo
>   4688 (creación de procesos). Ese es el rastro #1 para cazar malware… y está apagado por
>   defecto. **Pero** — recuerda que este host corre **Sysmon64**: Sysmon **Event ID 1**
>   cubre justo esa brecha con más detalle (hash, línea de comandos, proceso padre). Ejemplo
>   perfecto de *defensa en profundidad*: donde la auditoría nativa está ciega, Sysmon ve.
> - **`Object Access` y `Sensitive Privilege Use: No Auditing` ⚠️** — el acceso a archivos,
>   registro, SAM y el uso de privilegios sensibles (SeDebug) **no** se auditan. Habilitarlos
>   genera mucho ruido, por eso vienen apagados; un SOC los activa selectivamente sobre activos
>   críticos.
>
> **Conclusión del bloque:** la telemetría nativa tiene huecos deliberados. Un atacante que
> apaga las categorías que *sí* están activas (T1562) o limpia el log (T1070) borra sus huellas
> — por eso auditar la política **misma** es parte del chequeo defensivo.

Un atacante que quiere borrar sus huellas suele **deshabilitar categorías de auditoría**
o **limpiar el log de Seguridad** antes de salir — por eso auditar la política misma
(¿sigue habilitada la auditoría de logon?) es parte del chequeo.

</details>

### 4.4 Process Explorer (Sysinternals, estándar)

Se ejecuta `procexp64.exe` desde el USB — no requiere admin para la vista básica. Se activa
**Options → Verify Image Signatures** para ver de un vistazo qué procesos están firmados
(columna verde) y cuáles no. Se agrega la columna **Integrity Level** para ver en qué nivel
corre cada proceso, y se usa el panel inferior (`Ctrl+D`) para inspeccionar las DLLs cargadas
por un proceso seleccionado.

![Process Explorer mostrando procesos con su Integrity Level y firma](/assets/images/tema06/procexp01.png)

> **Tarea de informe:** con *Verify Image Signatures* activo, se anota si aparece algún proceso
> **`(Not verified)`** (sin firma válida) o con un **Integrity Level** inusual (p. ej. un proceso
> de usuario corriendo en *High* sin razón). Pista para este host: aparecen `Sysmon64.exe` y el
> agente de Elastic entre los procesos — firmados y en su nivel esperado. Un proceso sin firma
> ejecutándose desde `AppData` o `Temp` es la señal a documentar.

### 4.5 TCPView (Sysinternals, estándar)

Se ejecuta `tcpview.exe` — muestra en tiempo real cada conexión TCP/UDP activa con su proceso,
dirección remota y puerto. Un patrón de **beaconing** (comunicación C2) se ve como
conexiones **periódicas** hacia la misma IP/dominio poco reconocible, a intervalos
regulares — sin que el usuario haya iniciado nada. Aquí **solo se observa**: no se genera ni
provoca tráfico malicioso alguno.

![TCPView mostrando conexiones TCP activas con proceso y destino](/assets/images/tema06/tcpview01.png)

> **Tarea de informe:** se anotan 3-5 conexiones activas reales — proceso, dirección remota y
> puerto — y se clasifican: ¿se reconoce el proceso (navegador, actualizador de Windows, el
> agente de Elastic enviando telemetría)? En este host es esperable ver al **Elastic Agent** con
> conexiones salientes hacia su servidor. Se documenta solo **lo que realmente se observa** — el
> objetivo es distinguir tráfico legítimo de un patrón de *beaconing* (conexiones periódicas a
> un destino desconocido), no inventar un hallazgo.

### 4.6 Mapeo ATT&CK

| Técnica ATT&CK | Nombre | Por qué aplica aquí |
| -------------- | ------ | -------------------- |
| **T1070** | Indicator Removal | Borrar o deshabilitar el log de Seguridad / la política de auditoría para ocultar actividad. |
| **T1057** | Process Discovery | Process Explorer es exactamente la herramienta con la que un defensor (o un atacante) enumera procesos y su contexto. |
| **T1049** | System Network Connections Discovery | TCPView enumera las conexiones de red activas del sistema. |

### Resumen del tema

- Un endpoint Windows trae **capas nativas de defensa** apiladas: identidad/privilegios,
  superficie/ejecución activa y telemetría/auditoría — auditarlas no requiere admin para
  el flujo principal.
- **Identidad y privilegios:** SID, grupos, Integrity Levels y UAC determinan qué puede
  tocar un proceso sin consentimiento explícito; las ACLs NTFS refuerzan esa barrera a
  nivel de archivo.
- **Superficie y defensa activa:** Autoruns revela dónde persiste el software, Windows
  Defender bloquea/detecta ejecución maliciosa (salvo exclusiones), y el Firewall filtra
  conexiones entrantes por perfil de red.
- **Telemetría y auditoría:** Event Viewer, Process Explorer y TCPView son la última línea
  — no previenen, pero permiten **reconstruir** lo que pasó.
- Cada mecanismo de defensa se mapea a una técnica **MITRE ATT&CK** concreta, y ese mapeo
  se puede **cruzar con el TIM** (tema05) para ver qué actores y malware reales la usan.
